# Промпты, решения, ограничения

## Как устроена защита от выдуманных характеристик

Одного запрета в промпте недостаточно, поэтому защита многоуровневая.

1. **Характеристики вообще не пишет модель.** Таблица «Ключевые характеристики» собирается кодом из полей входа дословно. Если характеристик нет, в таблице стоит «данных нет». Модель пишет только текстовые блоки.
2. **Модель видит только непустые данные** плюс список `not_provided`: чего во входе нет. Так она знает, о чём молчать.
3. **Промпт** ([cardgen/prompts.py](cardgen/prompts.py)) жёстко определяет единственный источник фактов, запрещает расшифровывать маркировку модели из названия и использовать знания о «типичных параметрах серии», разрешает только короткое нейтральное пояснение типа прибора без чисел, сред и отраслей.
4. **Автопроверка чисел** ([cardgen/checks.py](cardgen/checks.py)): все числа в сгенерированном тексте должны встречаться во входных данных (запятая и точка равнозначны). Иначе модель получает список проблем и переделывает ответ.
5. **Если после всех попыток проблемы остались**, карточка не скрывается, а выдаётся с разделом «Требует ручной проверки». Контент-менеджер видит, что именно не прошло.

## Промпт

Системный промпт состоит из четырёх частей:

- роль (технический редактор B2B-магазина КИП, результат — черновик для человека);
- блок «никаких выдуманных характеристик» с пятью конкретными правилами;
- требования к каждому полю результата (длины, стиль, чего не писать: цены, гарантии, сроки, наличие);
- требование вернуть ответ строго в структурированном виде: через вызов инструмента (Anthropic) или одним JSON-объектом (остальные провайдеры).

Решения по промпту:

- **Структурированный ответ в двух режимах.** Для Anthropic используется tool use с принудительным `tool_choice`. Для OpenAI-совместимых провайдеров (Groq, OpenRouter, Ollama) — JSON-режим с точным описанием формата в промпте: он поддерживается шире, чем вызов инструментов у бесплатных моделей. Если провайдер отвечает 400 на `response_format`, запрос повторяется без него. Разбор терпим к обёрткам ```` ```json ```` и к блокам `<think>`, а проверка и повторные попытки одинаковы для обоих режимов.
- **Правила сформулированы через «можно только если дословно есть во входе»**, а не через список запрещённого. Список запрещённого всегда неполон.
- **`missing_data` — только названия характеристик, без значений.** Подсказка менеджеру, что запросить в паспорте. Она опирается на знание о типе прибора, но не утверждает ничего о конкретном изделии.
- **При бедных данных объём набирается общим пояснением о типе прибора, а не выдумками.** Первая версия промпта просила честно писать «данных нет» прямо в описании: текст получался коротким и содержал фразы вроде «в карточке отсутствует описание», неуместные на сайте. Теперь нехватка данных вынесена в поля для менеджера (`manager_notes`, `missing_data`), а в описание допускается 2–4 нейтральных предложения о том, для чего служат приборы этого типа, без чисел и без утверждений о конкретной модели. В конце одна фраза про уточнение по паспорту.
- **Запрещены расшифровка названия модели и приписывание достоинств.** По результатам живых запусков модель писала «относится к серии…», «выполнена в исполнении…» (расшифровка маркировки, которой нет во входе) и «удобство считывания», «компактные габариты». Это прописано отдельными правилами.
- Температура не задана явно, чтобы код работал с разными моделями без правок. При необходимости добавляется одним параметром в `llm.py`.

## Принятые решения

| Решение | Почему |
|---|---|
| Проверка длины и чисел кодом, а не доверие модели | LLM плохо считает символы и может «подмешать» цифры. Это дёшево проверить |
| До 3 попыток, в повторе модель получает конкретный список проблем | Обычно хватает одной правки; ограничение защищает от лишних расходов |
| В повторе модели показывают её собственный текст и просят добавить один абзац заданного размера | Проверено на бесплатной модели: просьба «перепиши длиннее» давала текст ещё короче (685 → 461 → 457 символов), а «дополни» — повтор уже написанного |
| Слишком длинное описание (> 1200) обрезается кодом по границе предложения, завершающая фраза про паспорт сохраняется | Модель игнорирует просьбу сократить (вернула тот же текст). Код только удаляет целые предложения и ничего не дописывает; если после обрезки текст стал бы короче 800, он не трогается. Факт обрезки виден в `stats.seo_description_trimmed` |
| Проверка повторов: предложение, на 70% и более совпадающее по словам с более ранним, считается повтором | Для набора объёма модель копировала абзац почти дословно (ТРМ251: второй абзац повторял первый). Модель получает повтор с просьбой добавлять только новые по смыслу пояснения |
| Список «опасных» слов (места установки, отрасли, автономность, «компактный», «относится к серии»), которых нет во входе | В живых запусках бесплатная модель дописывала «в трубопроводах, резервуарах», «работает автономно и не требует питания». Числовая проверка этого не видит. Если слово есть во входе, оно разрешено; при нарушении модель получает повтор с перечнем найденного |
| Ошибки API превращаются в понятные сообщения (401, 403, 404, 429, таймаут, нет сети) | Контент-менеджер не должен читать трейсбек |
| При 429 и 5xx запрос повторяется с паузой (учитывается `Retry-After`); без заголовка при 429 ждём 10, 20, 40 с. Ошибка провайдера внутри ответа 200 тоже повторяется | У бесплатных тарифов лимиты маленькие и действуют минутами, короткий всплеск не должен ломать запуск. Дневной лимит так не обойти: он сбрасывается раз в сутки |
| OpenAI-совместимый клиент написан на `urllib`, без SDK | Нулевые зависимости: запуск на чистой машине без `pip install`, бесплатные провайдеры подключаются одним ключом |
| Провайдер выбирается по заданному ключу, сменить можно флагом или переменной | Один и тот же код работает с Groq, OpenRouter, локальной Ollama и Anthropic |
| В списке один неверный товар не роняет остальные | Пропускается только он, код возврата 1 |
| Пустые значения и маркеры «n/a», «-», «нет данных» считаются отсутствием данных | Так выглядят реальные выгрузки |
| Результат в `.md` и `.json` | Markdown копируется в CMS, JSON — для интеграций |
| `--dry-run` | Позволяет проверить вход и увидеть, что уйдёт в модель, без расходов |
| Только CLI, без веб-формы | Задание допускает JSON или форму; CLI проще и надёжнее для прототипа |

## О тестовых данных из фида

Фид souz-pribor.ru содержит около 48 тысяч позиций. В просмотренной выборке (первые 3000 товаров) у позиций есть название, тип, производитель, цена, ссылка и артикул, но нет технических характеристик и описаний. Из двух выбранных приборов ОВЕН (ТРМ251-Н.РРР и ДТС065Л-РТ100.В4.160) нельзя узнать диапазоны, классы точности, питание и интерфейсы.

Поэтому это хороший тест главного требования: сервис обязан не выдумывать и честно указать, что данных нет. Для проверки сценария с богатыми данными в `examples/` лежит товар из текста задания. Цена и ссылка из фида в модель не передаются: цена быстро устаревает, а ссылка нужна только для справки в карточке.

## Ограничения

- **Качество описания зависит от входа.** При пустых характеристиках текст будет общим по назначению типа прибора. Это сознательный выбор в пользу честности.
- **Бесплатные модели слабее платных.** Они чаще нарушают длину описания и точнее следуют инструкциям не всегда. Именно поэтому есть автопроверка с повторами, но на сложных случаях может понадобиться ручная правка. Бесплатные лимиты и список моделей меняются, актуальные условия смотрите у провайдера.
- **Проверка выдумок: числа и короткий список стоп-слов.** Остальные нечисловые выдумки (материал, наличие сертификата, детали конструкции в `missing_data`) ловятся только промптом и ревью человека. Список стоп-слов составлен по реальным случаям и не претендует на полноту.
- **Число из входа может быть использовано не к месту** (например, артикул принят за параметр). Автопроверка этого не заметит.
- **SEO-запросы строятся без данных о реальном спросе** (нет частотности из Вордстата или подобных сервисов).
- **Нет разбора PDF-паспортов:** фрагмент паспорта нужно вставить в `description` текстом.
- Нет веб-интерфейса, хранения истории и пакетной обработки больших каталогов (одна последовательная очередь).
- Результат всегда нужно сверять с паспортом изделия перед публикацией.

## Что можно улучшить

1. Загрузка паспортов (PDF) и извлечение из них характеристик отдельным шагом с цитатой-источником для каждого значения.
2. Для каждого значения характеристики хранить ссылку на место во входе, чтобы менеджер мог быстро проверить.
3. Проверка нечисловых утверждений второй моделью («есть ли это во входе?»).
4. Подбор запросов по данным частотности и анализу выдачи.
5. Пакетный режим с параллельными запросами и кэшем, чтобы не платить за повторную генерацию.
6. Простая веб-форма (например, FastAPI + одна страница) и экспорт в формат импорта CMS.
7. Набор эталонных товаров с автоматической оценкой качества (регрессионные тесты промпта).
